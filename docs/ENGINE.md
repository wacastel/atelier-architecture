# Atelier engine notes

Atelier is a native macOS executable written in Swift and Metal Shading Language. It currently renders one static architectural scene at a time. Its first project is a deterministic Eiffel Tower reconstruction with human-scale viewpoints, terraces, an illustrative interior, geometric connections, and a contextual city.

The generated scene contains more than two million triangles. The current counts and allocations are reported by the executable and [the latest self-test report](../output/validation.json); [VALIDATION.md](VALIDATION.md) retains the original-release baseline separately. Generated detail counts describe this model, rather than original historical tower components.

## Application and scene flow

`ArchitectureMain` routes export and validation arguments before starting AppKit. The desktop application embeds an `MTKView` beneath a SwiftUI interface. `EngineController` builds the scene, Metal renderer, and navigation BVH off the main queue, then handles camera input, tour playback, accumulation resets, and measured performance updates.

`SceneData` is the common scene boundary. It stores unindexed triangles, smooth or face normals, a material index per triangle, a compact material array, and explicit light sources. `EiffelScene.build()` creates this data procedurally. `OBJScene` provides a second import path for command-line renders. The imported object receives an automatically framed camera; interactive scene selection and imported-building tour authoring are not implemented.

The Swift/Metal ABI uses 16-byte fields: `SceneVertex` and `SceneMaterial` each occupy 32 bytes, `FrameUniforms` occupies 128 bytes, `SceneLight` occupies 64 bytes, and `TemporalUniforms` occupies 112 bytes. The validation command checks these strides before issuing GPU work.

## GPU rendering

The renderer queries `MTLDevice.supportsRaytracing`, creates a native Metal command queue, and compiles the bundled shader as Metal language version 3.1. All scene triangles are placed in one `MTLPrimitiveAccelerationStructure`. The geometry is opaque and static. The closest-hit and shadow queries use Metal's triangle intersectors, including an any-hit query for shadow occlusion. Apple describes this acceleration-structure/intersector model in [Ray tracing with acceleration structures](https://developer.apple.com/documentation/metal/ray-tracing-with-acceleration-structures) and [Your guide to Metal ray tracing](https://developer.apple.com/videos/play/wwdc2023/10128/).

The compute kernel generates one jittered camera sample per pixel per dispatch. It evaluates an analytic sky and sampled finite sun, then traces a bounded sequence of surface interactions. The BRDF combines diffuse reflection with GGX microfacet reflection, Schlick Fresnel, Smith masking, and metallic/roughness parameters. The path sampler mixes diffuse and specular sampling and uses Russian roulette after the early bounces. Emissive surfaces contribute when a path hits them; there is no explicit importance sampling of emissive meshes.

Direct sunlight uses next-event sampling and a traced visibility ray. At night, explicit uplights and local lamps use inverse-square attenuation, cone falloff and traced shadow visibility. A diffuse/specular continuation ray gathers indirect light and reflections, with visible-normal GGX sampling for glossy paths. Shader-side procedural patterns provide paving joints, coating variation, timber grain, vegetation variation, roofing seams, and opaque reflective glazing. Approximate pixel-footprint filtering reduces fine-pattern shimmer. Connection plates, flanges, rails, and rivet heads remain real triangle geometry. [Night implementation and photographic references](NIGHT.md).

Samples accumulate in a private `rgba32Float` texture. Camera movement starts new raw path accumulation while retaining separately reconstructed lighting history. Deterministic primary rays provide world position/material, normal/depth and albedo/roughness guides. Current world positions reproject into the previous camera; visibility tests reject mismatched or newly revealed surfaces. Luminance clipping limits stale history, followed by three surface-aware à-trous filter passes. This runs in Metal before exposure and tone mapping. It is a custom reconstruction for static geometry, without learned reconstruction or MetalFX integration. [Motion pipeline, shader contract and limitations](MOTION.md).

Camera cuts, timeline seeks, lighting, exposure, quality and resolution changes clear reconstruction history. An unchanged paused or manually stationary view stops tracing at 4,096 raw samples and continues presenting the refined image. A fullscreen pass applies an ACES-inspired fitted tone curve and explicit sRGB encoding to a `bgra8Unorm` drawable. Raw/still presentation retains a small low-sample depth/luminance filter; reconstructed frames bypass that older filter.

The integrator deliberately limits sample luminance to reduce fireflies and adds a simple distance haze. These choices introduce approximation and bias. This implementation does not claim an unbiased reference integrator, full spectral transport, multiple importance sampling, volumetric transport, or accurate glass transmission.

Dedicated hardware ray traversal depends on the actual GPU family. The program's `supportsRaytracing` check establishes Metal API availability; that Boolean alone is not a hardware-generation test. The engine delegates traversal to Metal instead of maintaining a software ray tracer. Apple's [hardware ray tracing discussion](https://developer.apple.com/videos/play/tech-talks/111375/) explains the hardware path and relevant intersector optimizations; [Metal capability tables](https://developer.apple.com/metal/capabilities/) distinguish feature availability by GPU family.

## Memory and frame scheduling

Vertex, material-index, material and light buffers use `storageModeShared`. The GPU reads CPU-created data from unified memory. Accumulation, reconstruction guides/history and acceleration-build scratch resources use private storage. This follows Apple's storage-mode distinction between shared CPU/GPU access and GPU-only resources. [Choosing a resource storage mode for Apple GPUs](https://developer.apple.com/documentation/metal/choosing-a-resource-storage-mode-for-apple-gpus).

The app permits up to two interactive command buffers in flight. GPU work is submitted through one queue. A frame encodes two path-tracing dispatches in Interactive mode, or four in Balanced and Ultra mode, plus primary guides, reconstruction and presentation, until the unchanged view reaches its accumulation cap. Each path dispatch adds one sample per pixel. Still export uses that queue and batches up to 32 ordered sample dispatches into each command buffer, waiting once per batch instead of once per sample. Video uses the preview path, preserving valid reconstruction history across frames. Output is presented into a shared texture before CPU readback.

The performance panel reports measured frame cadence, the most recent GPU command-buffer duration, accumulation count, triangle count, and `MTLDevice.currentAllocatedSize`. Interactive GPU frame time includes all samples submitted for that frame plus presentation; after reaching the stationary cap it measures presentation alone. Offscreen sample time is the final completed batch's GPU duration divided by its sample count, so the final presentation cost is amortized across that batch. The allocation metric covers the process's Metal resources, not all system memory or a peak resident-memory measurement.

Interactive quality caps render width at 960 pixels and uses two path interactions; Balanced caps width at 1440 with three, and Ultra at 2560 with five. Height follows the viewport aspect ratio. The image is linearly sampled to the actual drawable size. This is resolution scaling rather than MetalFX upscaling. The app requests a 60 Hz draw cadence; actual throughput depends on scene, view, resolution, reconstruction, lighting and GPU load. The live panel reports runtime measurements. The original-release snapshot in [VALIDATION.md](VALIDATION.md) predates the additional night lights and reconstruction passes.

The Mac's 512 GB unified-memory capacity leaves substantial room for future data, but this scene does not need or reserve that capacity. There is currently one full static mesh, one GPU acceleration structure, and a CPU navigation BVH. No sparse residency, streaming, acceleration-structure instancing or compaction, meshlets, automatic LOD, out-of-core rendering, or large-scene memory-budget manager is implemented. A large memory specification does not establish large-scene performance; measured stress tests remain necessary.

## Navigation and demo

Fly mode moves freely along the camera orientation, with separate vertical movement. Walk mode flattens forward movement, limits movement speed, and uses a downward support ray to follow floors. Head, torso, and lower-body ray sweeps provide simple obstacle rejection. Small decorative triangles are omitted from the CPU collision representation; the rendered scene retains them. This is a lightweight camera controller, not a rigid-body or character-physics simulation.

The eight authored viewpoints cover exterior form, the arches, close ironwork, first-floor terrace, pavilion interior, second terrace, summit, and final exterior. `WalkthroughPlayback` owns a renderer-independent state machine, an elapsed walkthrough clock and a separate idle clock. View selection resets to slow idle motion; each view has its own 56-second route. Space starts, pauses and resumes without resetting elapsed time. The pace choices are 0.25×, 0.5×, 1×, 2× and 4×. Left/right shuttle presses cycle 2×, 4× and 8× relative to that pace; operating-system key repeats are ignored. Up/down and number keys select views, with wraparound for up/down.

The opening idle orbit advances 0.35 degrees per second; its walkthrough completes a full orbit in 56 seconds. Other routes use smooth interpolation along authored clear line segments, without spline overshoot, for the arches, ironwork, terraces and pavilion. Camera targets and field of view change along each route. Walkthrough endpoints pause; paused cameras do not revert to idle. WASD or dragging takes manual control. The Idle button returns to the selected bookmark. These routes are individual studies, without continuous elevator or inter-floor transitions.

PNG export uses the same path-tracing and presentation pipelines as the viewport. MP4 export runs frames through the reconstructed preview path and encodes them through AVFoundation as H.264, with captions and a progress bar. Reconstruction history persists within a route and clears at chapter cuts. `--raw` disables motion reconstruction for video comparisons. Export currently runs synchronously, and a desktop screenshot can briefly pause interaction while its 32 samples are rendered.

The default chaptered export maps all eight complete routes onto a 96-second recording with deliberate cuts. `--single-view --stop N` exports one route, defaulting to 56 seconds; `--seconds` retimes the complete route. `--idle --stop N` uses the actual idle clock for the requested recording length. The original-release demonstration and stills remain separate artifacts, documented in [DEMO.md](DEMO.md). They predate the updated routes and reconstruction.

## Validation and build

`--self-test` checks finite vertex data, GPU ABI layout, material/triangle consistency, Metal pipeline and acceleration-structure construction, a nonblank rendered image, changing progressive accumulation, the final sample count, a ground intersection through the navigation BVH, and the OBJ importer's checks. It writes an image and a JSON report. These checks establish basic rendering and data-path behavior; they do not certify physical accuracy, historical accuracy, every tour location, or all navigation cases. Tour views and app interaction also need visual inspection.

`swift scripts/validate-metal.swift` independently builds a two-triangle GPU acceleration structure, compiles the production trace and presentation shaders, and dispatches a 32 × 32 render. It verifies finite RGB and a known five-metre hit, then compares a two-sample accumulation against the arithmetic mean of separately rendered samples. The current regression run passed with exactly zero maximum mean error and an exact frame-zero reset. [Recorded checks and reproduction commands](VALIDATION.md).

`scripts/validate-playback.sh` exercises clock state, pause/resume, all pace settings, shuttle cycling, seeking, endpoint clamps, view wrapping and invalid timestamps. It also samples each complete authored route at 560 positions and each idle animation at 120 positions against the actual navigation BVH, checking body/camera clearance and supported walking paths. `swift scripts/validate-denoiser.swift` executes synthetic Metal reconstruction tests; `--motion-test directory` additionally compares moving Eiffel overview/iron images against independent high-sample references and writes image/error artifacts. [Motion tests](MOTION.md).

The package has no third-party dependencies. `scripts/build-app.sh` creates a release arm64 executable, copies the SwiftPM resource bundle and prebuilt `assets/Atelier.icns` into `Atelier.app/Contents/Resources`, writes an application property list, applies an ad-hoc signature, and verifies the bundle. The original icon is generated from CoreGraphics paths by `swift scripts/create-icon.swift`; ordinary builds use the prebuilt icon and do not regenerate artwork. `MetalRenderer` first looks in the application's packaged resources and falls back to `Bundle.module` when run from a SwiftPM build. The launcher rebuilds when source or shader resources are newer than the app executable. The application is for local use and is not notarized or installed globally.

## Architectural fidelity

The tower's published 330 m height, 125 m ground footprint, and 57 / 115 / 276 m principal floors establish the scene's scale. The monument operator also documents 18,038 iron parts and 2.5 million original rivets. The reconstruction represents selected connections and repeating structural patterns; it does not reproduce that complete historical parts inventory. [Official Eiffel Tower figures](https://www.toureiffel.paris/fr/le-monument/chiffres-cle).

Detailed limitations and modeling choices belong in [MODEL.md](MODEL.md). A surveyed reconstruction would need licensed survey data, historical or current construction drawings, calibrated photographic material capture, and separate validation of the visitor interiors. The current surroundings and interior furnishings are authored context.

## Next engineering steps

1. **Further motion fidelity:** refine residual noise, newly revealed thin geometry and view-dependent reflections; evaluate MetalFX or learned reconstruction against the custom temporal/spatial pipeline. Animated objects would require object-motion data beyond the current static-world reprojection.
2. **Large buildings and cities:** partition and instance geometry, compact acceleration structures, add explicit memory budgets and streaming, and benchmark scene sizes and camera traces on the target Mac Studio.
3. **Material fidelity:** implement texture ingestion, UVs, normal mapping, physically meaningful dielectric transmission, emissive-light importance sampling, and a calibrated environment-light workflow.
4. **Architectural data:** add validated USD/glTF or BIM ingestion, object identity, units, metadata, and a scene/tour authoring interface; preserve provenance for survey assets.
5. **Navigation:** improve continuous collision handling, traversable stairs, doorways, elevators, accessible paths, and safe saved-view transitions.
6. **Rendering validation:** add reference scenes for energy behavior, BRDF sampling, glass and emitters; compare renders with independent reference images and track performance regressions using fixed camera paths.
